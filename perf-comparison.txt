Performance comparison: jp_alloc vs system tup (tup parse -q)
=============================================================
Date: 2026-07-30
Project: ~/work/bes_devel.cov
Setup: 3 variants (debug, debug-cov, release), 2897 Tupfiles, 37774 source files
Method: Full first-time parse (rm -rf .tup build-* && tup init && tup variant tup/variants/* && tup parse -q)
All binaries built with CFLAGS="-g -O2"
Iterations: 3 per binary

Binaries
-------
SYS = system tup 0.8-man12 (/usr/bin/tup)      distro package, libc malloc
NEW = jp_alloc (C conversion, d72b8b5e+)        build/tup from build.sh

Results
-------
                  SYS (tup 0.8)    NEW (jp_alloc C)
Time avg:         58.6s            53.6s             -8.5% faster
Peak RSS avg:     313 KB           372 KB             +19%  (+59 MB)

Per-iteration
-------------
SYS iter 1: 0:59.15  RSS=313216 KB
SYS iter 2: 0:58.25  RSS=313496 KB
SYS iter 3: 0:58.45  RSS=312764 KB

NEW iter 1: 0:53.71  RSS=373292 KB
NEW iter 2: 0:53.72  RSS=371700 KB
NEW iter 3: 0:53.40  RSS=372276 KB

Analysis
--------
Time: jp_alloc is 8.5% faster than system tup 0.8. Lock-free CAS
freelists and headerless sized allocations give a consistent edge.

RSS: jp_alloc uses +59 MB (19%) more than system tup. The increase is
from power-of-2 rounding waste (up to 60% for struct tent_tree). libc
malloc uses tighter size classes with less per-object waste.

Trade-off: ~8.5% faster parse for ~19% more transient memory (freed
at exit). The memory overhead is inherent to the buddy-allocator design.

--- Tagged-pointer ABA fix benchmark (2026-08-05) ---
Project: ~/work/bes_devel.cov
Setup: 3 variants (debug, debug-cov, release), 2897 Tupfiles, 37774 source files
Method: Full first-time parse (rm -rf .tup build-* && tup init && tup variant tup/variants/* && tup parse -q)
All binaries built with CFLAGS="-g -O2", release (no JP_ALLOC_DEBUG)
1 warmup run per binary, then 5 alternating iterations

Binaries
-------
UPSTREAM = pre-fix jp_alloc C conversion (a10b1037)   /tmp/tup-upstream
TAGGED   = jp_alloc + tagged-pointer ABA fix (a10b1037+)

Results
-------
                      UPSTREAM          TAGGED-CAS
Time avg:             61.01s            59.55s            -2.4% faster
Time median:          60.93s            59.74s
Peak RSS avg:         312550KB          372094KB          +19% (+59MB, unchanged)

Per-iteration
-------------
UP  iter 1: 59.91s  RSS=312112KB    TAG iter 1: 58.86s  RSS=372420KB
UP  iter 2: 60.93s  RSS=312316KB    TAG iter 2: 59.74s  RSS=372340KB
UP  iter 3: 61.21s  RSS=312508KB    TAG iter 3: 59.91s  RSS=371924KB
UP  iter 4: 62.30s  RSS=313084KB    TAG iter 4: 60.10s  RSS=372140KB
UP  iter 5: 60.72s  RSS=312728KB    TAG iter 5: 59.15s  RSS=371644KB

Analysis
--------
Time: The tagged-CAS fix is ~2.4% faster than the pre-fix jp_alloc.
The 128-bit cmpxchg16b adds a small per-CAS cost, but eliminating
ABA-induced cache-line bouncing and spurious retries more than
compensates. The fix is both a correctness and a performance win.

RSS: Memory usage is unchanged (+59MB, +19%), as expected — the tag
occupies space already available in the 16-byte pool head struct and
does not affect per-block allocation sizes.
